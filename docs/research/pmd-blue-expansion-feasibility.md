# PMD Blue Rescue Team expansion feasibility: public tooling

Checked 2026-10-31. Public project repository READMEs, release notes and maintainer documentation establish advertised scope, not runtime verification in this investigation.

## NdsForge.NET local findings

The coordinating agent inspected NdsForge.NET at commit `2731747`. It found ROM image editing/building and overlay replacement infrastructure, but no PMD-specific codecs in the inspected source. The supplied `Pokemon Mystery Dungeon - Blue Rescue Team (USA).nds` SHA-256 exactly matches the existing `APHE-4bdf72ce0dd7.json` corpus record. This is useful evidence that the exact input is already represented in the corpus; it does not establish arbitrary PMD content editing, engine expansion, or gameplay correctness. No new build or gameplay tests were performed during this feasibility investigation.

Engineering interpretation: NdsForge can supply the generic DS container and build layer for a Blue project. The missing work is chiefly a Blue-specific data model, import/export compilers, versioned engine patches, and gameplay/save validation. Existing generic infrastructure materially improves feasibility without making NdsForge equivalent to a game-specific expansion codebase.

## Finding

I did not find an existing general-purpose **Blue Rescue Team** equivalent of pokeemerald-expansion, nor a public matching `pmd-blue` decompilation, in the searches below. This is a bounded discovery result, not proof that no private or obscure project exists. Closest useful alternatives are **pmd-red** for source-level work on Rescue Team, **Rogue Rescue Team / Shiny Patch** for existing Red engine modifications, and **SkyTemple** for an established DS PMD editing and patch ecosystem targeting Explorers of Sky.

## Practical implications (engineering inference)

1. **A useful Blue modding base is realistic without a complete matching decompilation.** Start with a deterministic ROM build, typed editable content, documented version-specific hooks and a small set of tested engine patches.
2. **A pokeemerald-expansion-sized Blue platform is much larger.** Container editing, overlay replacement and sprite extraction do not resolve species-table limits, ID handling, moves/abilities, save compatibility, memory budgets, event semantics or patch interaction. These require game-specific reverse engineering and testing.
3. **Red knowledge reduces discovery work but is not a binary port.** The cutsceneless project's shared-script technique is concrete evidence of reusable knowledge; pointers and DS-specific runtime behavior still differ. Port semantic logic only after validating the Blue target.
4. **Choose the platform before investing.** For Blue-on-DS specifically, build the missing layer atop NdsForge and study existing Blue utilities. For Rescue Team source-level expansion with platform flexibility, pmd-red is materially closer to the requested starting point. For a new DS PMD adventure with many editor features already available, SkyTemple is the pragmatic alternative. For native PC/.NET exploration, pmd-green is relevant but explicitly experimental.
5. **Define success with a vertical slice.** First demonstrate a clean rebuilt Blue ROM, one content edit visible in-game, one mechanics hook, and save/reload stability before estimating a large roster or generalized expansion project. No runtime claims or calendar estimates are established by this public-source investigation.

One packaging edge case worth testing: a current [ndstool issue](https://github.com/devkitPro/ndstool/issues/16) reports that Blue overlay IDs do not always equal their file IDs, causing incorrect labels in extraction. Treat this as a reported compatibility case for validation, not independently reproduced here.
