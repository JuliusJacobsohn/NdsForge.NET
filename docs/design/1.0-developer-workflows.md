# NdsForge 1.0 developer workflows

This document defines the tasks the public API must make natural before the
`1.0.0` surface is frozen. It complements the ndstool capability inventory: the
inventory establishes format and compatibility coverage, while this document
starts from what a .NET developer is trying to accomplish.

## Design principles

- Opening and validation are read-only. Nothing repairs, extracts, or rewrites an
  image as a side effect of parsing.
- Paths, streams, and memory are first-class inputs. Ownership and `leaveOpen`
  behavior are explicit, and large payloads remain streamable.
- Typed models retain raw bytes for reserved or not-yet-understood fields.
- Preservation editing and structural rebuilding are distinct workflows with
  distinct guarantees.
- Every write can produce a change plan before bytes are committed.
- Determinism is the default for new builds. Compatibility quirks require a named
  profile and never leak into the ordinary object model.
- Integrity and authenticity are different results. The library never calls an
  image authentic merely because stored hashes are internally consistent.
- Expected format defects are structured diagnostics. Exceptions represent an
  operation that cannot safely continue.

## 1. Open, inspect, and query

A developer must be able to open a path asynchronously, open a caller-owned
seekable stream with explicit lifetime behavior, or load existing memory. The
result exposes:

- common DS and lossless DSi header views;
- physical length, declared used length, and nominal cartridge capacity as
  separate values;
- ARM9, ARM7, ARM9i, and ARM7i Programs with payload streams, ROM Regions, load
  addresses, and entry addresses;
- NitroFS navigation by hierarchy, canonical path, and File ID;
- every Allocation, including unnamed Overlay payloads;
- ARM9 and ARM7 Overlay tables with both Overlay ID and File ID;
- Banner metadata, raw tiles/palettes, localized titles, animation words, and
  decoded frames;
- the logo and Secure Area as named structures rather than magic offsets.

Useful convenience APIs include `CopyToAsync` on files and Regions, recursive
directory enumeration, safe path lookup, and immutable region maps. LINQ remains
the normal answer for arbitrary queries; the library should not grow a second
query language merely to filter extensions or sizes.

## 2. Validate and investigate damaged images

`Validate` returns stable, location-bearing diagnostics for header/logo/banner
CRCs, region bounds and overlap, FNT/FAT relationships, Overlay links and memory
ranges, secure-area state, DSi digest trees, hashes, and signature structure.
Options select cost and trust inputs, not whether malformed bytes are silently
accepted.

Strict open constructs a fully valid navigable object graph or throws a format
exception. A separate probe/repair reader can inspect a damaged header and emit
partial raw findings without pretending it produced a normal `NdsImage`. This
avoids nullable-everything models whose invariants no developer can rely on.

Repair is plan-based. Named operations such as repair header CRC, banner CRCs,
secure-area CRC, device capacity, used size, and DSi digest tables add explicit
changes to an Edit Session. There is no ambiguous `FixAll()` that might alter
signed or encrypted content unexpectedly.

## 3. Extract components safely

Developers need both high-level workspace export and low-level streaming:

- export selected Programs, tables, logo, Banner, Overlays, and NitroFS;
- copy any Region or file to an arbitrary destination stream;
- filter named files with a predicate or a separately reusable glob matcher;
- choose fail, skip, or atomic overwrite behavior;
- cancel long operations and receive progress without console dependencies;
- emit a machine-readable workspace manifest recording identity, addresses,
  File IDs, Overlay links, hashes, and Layout facts needed for a later rebuild.

Directory extraction rejects traversal, host-reserved names, collisions, and
symlink/reparse-point redirection. Stream export has no host-path policy because
the caller owns the destination.

## 4. Make preservation-oriented edits

An Edit Session supports changes that can retain the source's structure:

- edit validated identity and card-control fields;
- replace a named NitroFS file or arbitrary Allocation;
- replace a Program, Overlay payload, Banner, or logo;
- edit localized titles and static/animated banner data;
- request named checksum or digest repairs;
- choose whether enlarged payloads may relocate and how their new starts align;
- inspect semantic and physical change plans before saving;
- revert individual changes or reset the session;
- save to a new stream or atomically replace a path, then reopen and verify.

Unchanged input produces byte-identical output. Shrinking or same-size replacement
uses the existing Allocation when policy permits. Growth preserves File IDs and
appends or relocates payloads without silently compacting unrelated Regions.

## 5. Change NitroFS structure

Adding, deleting, moving, or renaming entries triggers a Structural Rebuild
because the FNT and often the FAT must change together. The tree API supports
explicit empty directories, caller-owned payload streams, import from a host
directory, and ordered merging of several roots with a collision policy.

The rebuild policy makes File ID behavior explicit:

- `PreserveWherePossible` retains existing IDs, holes, and Overlay references;
- `Deterministic` assigns IDs by a documented stable directory/name order and
  rewrites dependent Overlay File IDs;
- `Compact` minimizes gaps while reporting every changed numeric identity;
- a named ndstool compatibility profile reproduces upstream ordering/layout only
  where differential fixtures prove the behavior.

Before commit, a change plan reports renamed paths, deleted/created allocations,
File ID remaps, Overlay updates, table growth, relocations, and capacity changes.

## 6. Build a new DS or DSi image

A Build Recipe combines independently testable components:

- image kind and typed identity metadata;
- raw binary or ELF-derived Programs with explicit addresses;
- optional Overlay definitions and payloads;
- a mutable NitroFS tree or imported workspace;
- Banner and caller-supplied logo;
- DS/DSi header template or typed DSi metadata;
- cartridge timing, alignment, padding, PassMe, secure-area, and capacity policy;
- deterministic or named compatibility Layout profile.

Build can target a stream or atomic path, exposes progress/cancellation, and
returns a report containing every final Region, File ID, checksum, warning, and
reproducibility input. Building the same recipe twice must produce identical
bytes unless the recipe explicitly supplies varying data.

## 7. Work with executables and Overlays

Raw program input remains simple: bytes plus load and entry addresses. ELF32
import is an adapter that validates class, endianness, machine, program headers,
physical/virtual address mapping, BSS, overlap, and entrypoint conversion before
it creates Program or Overlay descriptions. It never exposes a half-parsed ELF
as an NDS model.

Overlay editing includes table metadata, payload replacement, File ID linking,
compression state, RAM/BSS size, and static-initializer range validation. A
built-in overlay BLZ codec is useful if backed by independent format vectors;
game-specific compression formats remain extension points, not guesses in core.

## 8. Create and edit banners and logos

Core APIs operate on platform-neutral pixel buffers and native binary forms:

- render static or animated banner frames to RGBA32;
- build versions 1, 2, 3, and `0x0103`;
- set every supported language title with exact UTF-16 limits;
- set indexed pixels/palettes directly;
- deterministically quantize RGBA32 to the 16-color banner palette;
- build animation sequences with typed duration, tile frame, palette frame,
  horizontal flip, and vertical flip fields;
- decode and encode the cartridge logo's monochrome tiled form.

PNG, BMP, GIF, and GRF file parsing belongs in an optional `NdsForge.Images`
adapter. This keeps the core dependency-light while still giving application
developers a one-call path from common files when they install the adapter.

## 9. Handle secure areas and DSi integrity

Secure-area operations are pure transformations with distinct detection,
validation, decrypt, and encrypt entry points. They write to caller-selected
destinations and report whether the area was absent, plain, encrypted, malformed,
or successfully transformed. Key material and trust policy are explicit inputs;
the package contains no hidden environment or machine dependencies.

DSi validation covers sector hashes, block hashes, master hashes/HMAC structure,
Program and Banner HMAC fields, modcrypt Region consistency, and RSA signature
verification when the caller supplies a trusted public key. Rebuilding unsigned
or homebrew DSi images describes which integrity fields were recomputed, cleared,
preserved, or unverifiable.

## 10. Compare images and automate builds

A semantic diff reports header-field changes, component hashes, NitroFS path and
File ID changes, Overlay metadata/link changes, Banner changes, and physical
Layout changes. It complements, rather than replaces, a raw byte diff.

Stable manifest DTOs and JSON serialization allow build systems to inspect,
review, and reproduce recipes without automating console text. The CLI consumes
only public APIs and provides inspect, validate, extract, build, edit, repair,
diff, banner/logo, ELF, and secure-area commands.

## 1.0 acceptance map

The following are release gates, not stretch goals:

| Area | Required evidence |
|---|---|
| Read model | DS/DSi, nested/empty NitroFS, unequal Overlay/File IDs, every Banner version |
| Preservation | no-op byte equality; grow/shrink/same-size edits; atomic path and stream saves |
| Structural rebuild | randomized tree mutations; deterministic repeats; Overlay File ID remapping |
| New build | binary and ELF Programs; DS and DSi recipes; emulator boot acceptance tests where available |
| Integrity | CRC vectors, secure-area vectors, DSi digest corruption at every hierarchy level |
| Safety | truncation corpus, overflow/count/depth limits, hostile extraction names, cancellation |
| Compatibility | byte comparison with ndstool for every operation where its result is a valid oracle |
| Package | API/docs review, analyzer-clean builds, source/symbol package, clean install-and-run acceptance test |

## Deliberate scope boundaries

NdsForge is not a general sprite editor, emulator, disassembler, save-file editor,
game-specific archive toolkit, or copyrighted-asset distributor. Those tools can
consume its streams and models. Common image-file adapters, ELF ingestion, and
well-specified NDS-native compression are in scope because they directly bridge
developer inputs to Image components.
